## 1. 使用规则

1. 本文不是新的业务规范。2026-09-03 用户确认的
   [一期 18 节点范围基线](PHASE1_SCOPE_WITH_P0_MAPPING_20260903.md)优先决定一期范围、排除项和优先级；
   其余科学事实按[权威业务资料索引](../../../工作流设计/01-业务依据/README.md)读取。
   [数据契约](../../full-t01-mock-v0.1/工作流设计/02-数据契约/T01_Dify节点-MCP工具映射与数据契约_v0.1.md)
   是派生工程契约，不能反向覆盖范围或科学原件。
2. 负责人没有明确确认前，不得把建议、Mock 固定值或当前代码行为写成科学规则。
3. 每项关闭时必须同时留下：具名确认人、明确决定、适用版本、修改位置、验收用例和证据。
4. 若暂时无法决定，可标记 `DEFERRED`，但必须记录原因、临时边界和重新评审条件。
5. 本清单只覆盖 T-01 智能体、Dify 与 MCP/后端契约，不纳入另一项目的服务器部署事项。
6. 开放项按 [P0-P7 顺序交付计划](P0_P7_STAGE_DELIVERY_PLAN_20260903.md)随对应阶段收敛；首轮评审只是
   风险和未知项盘点。输出相关 OI 应先取得冻结候选工具的原始实测证据，再定稿 Schema；
   阈值、门控和业务语义仍须相应负责人确认。
7. 未来阶段的 OI 不阻塞 P0，但受该 OI 影响的工具不得在决定形成前进入生产化、工作流或
   `DEPLOYED` 状态；允许先做隔离、不可用于科研结论的 `discovery` 实测。

状态定义：

| 状态 | 含义 |
|---|---|
| `OPEN` | 尚未形成可执行决定 |
| `IN_REVIEW` | 已指定确认人，正在评审 |
| `DECIDED` | 决定已记录，但契约或实现尚未全部更新 |
| `DEFERRED` | 有明确理由和重启条件的延后项 |
| `BLOCKED` | 依赖外部输入，当前无法继续 |
| `VERIFIED` | 契约、实现、测试和证据均已更新 |

## 4. 优先评审包 B：异步长任务

关联项：OI-017。

### 已有契约

- 已定义 `jobs.get_status`、`jobs.get_result`、`jobs.cancel` 三个共享 MCP 工具。

依据：数据契约[第 4.7 节](../../full-t01-mock-v0.1/工作流设计/02-数据契约/T01_Dify节点-MCP工具映射与数据契约_v0.1.md#47-异步任务-mcp-契约)。

### 评审决定及 2026-09-03 范围更新

- 开放项：OI-017。
- 状态：`DECIDED`；状态机原则已决定，数据契约、Dify 子流程、后端实现和测试尚未完成，
  因此不能标记为 `VERIFIED`。
- 具名确认人及角色：wing（开发者）。
- 确认日期：2026-09-01。
- 适用范围：首个及后续真实异步科学工具；不为任何工具猜测运行时长、资源量或科学参数。
- 提交与幂等：原科学工具负责提交并返回 `job_id`。同一幂等键和同一规范化载荷必须返回
  同一 `job_id`；同键不同载荷确定性返回幂等冲突。v10 串行主路径中，一个 `run_id`
  同时最多存在一个活动科学作业，重复进入不得重复提交。
- 状态事实源：后端持久化状态是权威事实；Dify 追踪只用于观察。`jobs.get_status` 必须是
  只读查询，不得像当前 Mock 一样因轮询次数推进状态。`QUEUED/RUNNING` 不返回完整结果；
  终态结果由 `jobs.get_result` 幂等读取且内容不可变。
- 超时：工具 deadline 与整条 run deadline 均由版本化执行档案声明。deadline 到期后进入
  `FAILED` 并返回 `TIMEOUT`，不得误报成功或混同用户取消。
- 取消：用户取消最终进入 `CANCELLED`。取消请求发出后，在 worker 确认前仍保持
  `QUEUED/RUNNING` 并记录 `cancel_requested=true`；完成与取消竞态以首次持久化终态为准。
  对终态重复取消返回原终态和 `cancel_applied=false`，不得制造新的 `FAILED`。
- 恢复：建设可复用的 `T01_AwaitJob` 有界等待流程。短等待窗口内仍未终结时，Dify 本轮
  返回 `run_id`、`job_id`、当前状态和 `resume_after`；后续以相同 `run_id` 重新进入 Master，
  通过幂等重放找到原作业并从持久状态继续。
- 执行档案：每个真实工具上线前必须登记版本化 execution profile，至少包含同步/异步分类、
  初始轮询间隔、退避与最大查询频率、工具/run deadline、取消能力、可重试查询错误、并发限制、
  结果与产物保留期。没有完整档案不得启用 `production`。
- 当前边界：仅确认通用编排框架，不表示现有 Mock 状态推进、取消行为或主 DSL 已满足该决定；
  首个真实长任务接入前必须完成契约、实现与验收用例。

### 实施时仍需逐工具填写的执行档案

| 决策点 | 需要形成的结果 |
|---|---|
| 任务分类 | 哪些工具必须异步、哪些允许同步，以及每类任务的预计时长和资源级别 |
| 轮询策略 | 初始间隔、退避、抖动、最大查询频率，以及可重试查询错误 |
| 超时语义 | 单工具 deadline、整条 run deadline、超时后的后端状态和标准错误类别 |
| 结果与保留 | 何时调用 `get_result`、结果幂等性、作业/产物保留期限和过期行为 |
| 资源与取消能力 | 并发/配额、可取消阶段、取消原因与执行器确认方式 |

### 最小验收用例

1. `QUEUED -> RUNNING -> SUCCEEDED` 后只读取一次确定性终态结果。
2. `QUEUED -> CANCELLED`，以及取消与自然完成同时发生的竞态。
3. 可重试状态查询错误后恢复；不可重试错误立即得到标准化失败。
4. 达到单任务或整条运行 deadline 后，不把未知状态误报为成功。
5. Dify 中断后凭原 `run_id/job_id` 续查，不创建重复科学任务。
6. 重复提交、重复取结果和终态重复取消均满足确认后的幂等规则。
