## 1. 一页结论

S-07 位于 P0 的结构获取入口，负责判断是否已经找到一份可以直接用于后续分析的结构；如果没有，
才需要继续进行结构预测。S-07 实际包含输入读取、结构来源查询、序列与坐标核对、候选选择、产物
保存和结果判断，因此不是简单的“下载一个 PDB 文件”。

前期真实输出实验发现，原方案只能简单表达“找到结构”或“没有找到结构”，无法说明多条蛋白链、
坐标缺失、弱同源命中、AlphaFold DB 模型、正常无结果和外部服务故障等情况。若直接按原方案
开发，可能选错结构、错误跳过结构预测，或把系统故障误报成“没有结构”。

## 2. 为什么一个工具需要这些决定

流程图中的 S-07 是一个业务步骤：

```text
目标蛋白序列
  → S-07 获取已有结构
       → 选出合格已有结构：进入 S-09
       → 没有合格已有结构：进入 S-08
```

RCSB、AlphaFold DB 和 BLAST 是 S-07 内部可使用的三类信息来源，但不表示每次运行都必须同时
查询三者。现有资料也没有给出明确的查询顺序和提前停止条件。是否必查、先后顺序和 BLAST 的用途
仍需要在 D14/D16 中由算法负责人确认。

已确认的工程方向是按照版本化 profile 执行来源计划，并如实记录实际执行与未执行原因。建议的
科学策略候选是优先检查实验结构，必要时查询公共预测结构，再按批准规则决定是否执行 BLAST；
但这一先后顺序仍未构成最终来源策略，需由 D14/D16 确认。

## 3. 已确认决定

### D01：权威序列

- 问题：结构检索必须知道哪一条序列是权威输入。
- 影响：若 accession、数据库返回序列或其他字段能够覆盖用户序列，可能检索和分析错误蛋白。
- 决定：`protein_sequence` 是唯一权威序列事实源。
- 状态：`CONFIRMED`。

### D02：UniProt accession 的地位

- 问题：AlphaFold DB 等来源更适合使用稳定 accession，但用户当前只保证提供蛋白序列。
- 影响：把 accession 设为必填会阻止合法序列运行；把 accession 当权威又可能覆盖用户序列。
- 决定：UniProt accession 当前不是必填项；未来如启用，只能帮助检索，所有返回结构仍需与
  权威序列回验。
- 状态：`CONFIRMED`。

### D03：一个 run 只绑定一份冻结输入

- 问题：全局运行输入已经保存序列，如果 S-07 再接收第二份序列，系统会产生两个事实源。
- 影响：两份序列不一致时，检索、缓存、重试和结果追溯可能使用不同输入。
- 决定：每次运行都唯一绑定一份不可变的输入记录；相同序列可以用于多次独立运行。S-07 不重复
  接收第二份序列，由后端从该记录取得权威输入。检索规则只能使用经过批准的固定版本，不能由
  调用方临时修改科学参数。
- 确认人及日期：wing（开发者），2026-09-01。
- 状态：`CONFIRMED`。

### D04：完整保存结构候选层级

- 问题：一个 PDB 条目可能包含多个蛋白、chain、model 和 assembly，PDB ID 本身不能唯一表示
  实际使用的结构对象。
- 影响：只保存 PDB ID 会造成信息丢失，可能选错链、错模型或把不完整链当作完整结构。
- 决定：候选必须保存来源、entry、entity、chain、model、assembly 元数据和实际结构产物；链
  同时保存数据库内部 ID 与作者使用的 ID。最终选择规则留给算法负责人。
- 确认人及日期：wing（开发者），2026-09-01。
- 状态：`CONFIRMED`。

### D05：序列映射与坐标映射分开

- 问题：蛋白序列能够完全对齐，不代表结构文件中的每个残基都有三维坐标。
- 影响：若只保存一个覆盖率，后续 RSA、质量分析或突变位点分析可能访问不存在的坐标。
- 决定：分别保存“目标序列↔结构蛋白序列”和“结构蛋白残基↔实际坐标”两层映射。完整逐残基
  对应关系进入产物，主结果只保留数量、比例、范围和缺失区段摘要。
- 确认人及日期：wing（开发者），2026-09-01。
- 状态：`CONFIRMED`。

### D06：判断是否选出合格结构，不判断是否搜到结果

- 问题：弱同源命中、缺失大量坐标的 exact entity 和真正可直接使用的结构都可能被旧字段
  `structure_found=true` 表示。
- 影响：不合格候选可能错误跳过 S-08；外部服务故障也可能被伪装成正常无结构。
- 决定：成功 outcome 改为“已经选出合格已有结构”或“检索正常完成但没有合格已有结构”。前者
  进入 S-09，后者进入 S-08；搜索命中、候选和最终 selection 分开保存。
- 确认人及日期：wing（开发者），2026-09-01。
- 状态：`CONFIRMED`。

### D07：如实记录各来源是否执行

- 问题：正常空结果、没有合法查询 ID、未按 profile 执行、前序来源满足条件后短路、临时失败
  和永久失败容易被混成“无结果”。
- 影响：系统可能错误重试、掩盖故障，或声称已经查询某个实际上没有执行的来源。
- 决定：逐来源记录它是否属于本次计划、是否真正执行、执行结果或未执行原因。空结果、profile
  关闭、短路、缺少验证标识和失败必须分开。本决定不要求三种来源每次全部查询。
- 确认人及日期：wing（开发者），2026-09-01。
- 状态：`CONFIRMED`。

### D08：完整科学产物保存在后端

- 问题：结构文件、完整候选、BLAST archive 和逐残基映射体积较大；只留摘要会丢失证据，全部
  内嵌进一次接口响应又会造成传输、重试和持久化问题。
- 影响：后续可能无法复核结构选择，或因调用方限制而被迫删除科学事实。
- 决定：完整科学产物由后端可靠保存，对外只返回必要的结构化摘要和结果文件引用。后端结果不为
  某一个上层系统量身修改；未来进行系统集成时，也不能删减或改变后端保存的权威结果和科学产物。
- 确认人及日期：wing（开发者），2026-09-01。
- 状态：`CONFIRMED`。

### D10：正常无结果与 ToolError 的边界

- 问题：正常检索完成但没有合格结构，与超时、来源不可用、输出损坏或任务取消，都可能表面上
  表现为“没有返回结构”。
- 影响：若混在一起，系统故障会被误判为科学无结果并错误进入 S-08；正常无结果也可能被误报为
  工具失败而中断流程。
- 决定：只有版本化 profile 规定的必要来源均已得到可判定终态、候选评估完成且确实没有合格
  结构时，才返回成功 outcome `NO_ELIGIBLE_EXISTING_STRUCTURE` 并进入 S-08。超时、必需来源
  失败、输出损坏、输入非法和取消必须返回明确 ToolError，不得进入 S-08。部分来源失败是否允许
  降级由预先批准的固定来源策略决定，后端和任何上层调用方都不得临时猜测。
- 确认人及日期：wing（开发者），2026-09-01。
- 状态：`CONFIRMED`。

### D11：三类命中的最终定义

**目前情况**

前期实测发现，找到的结构大致有三种情况：一种与完整目标蛋白一致；一种来自目标蛋白，但经过
截短、突变或其他改造；还有一种不是目标本身，只是与目标相似的同源结构。

例如，1UBQ、6XRE 和 AlphaFold DB 中的 O15116 与目标序列一致；5XZC 只覆盖 TP53 的一部分；
6PPV 与目标只有 62.5% 的局部序列一致性。目前对它们的分类只是为了便于讨论，并不是已经批准的
科学标准。

**可能遇到的问题**

现在还不知道一处突变、一个表达标签或者一段截短，是否就应该改变分类；也不知道一个局部相似的
结构至少需要相似到什么程度，才能称为同源模板。如果没有统一规则，同一个候选可能被不同人员归
入不同类别，甚至把截短结构误当成完整目标结构。

**希望得到的解决方案**

希望算法负责人明确三类结构各自的定义、判断顺序和最低门槛，并说明单点突变、天然变异、截短、
标签、融合蛋白和局部结构域分别怎样处理。对于证据不足的候选，也需要允许给出“暂时无法归类”，
而不是强行三选一。最后用本次已经实测的几类样本验证这些规则是否清楚可用。

---

### D12：已有结构是否达到可直接使用的门槛

**目前情况**

6XRE 的蛋白序列与 393 个氨基酸的目标完全一致，但其中只有 314 个目标残基具有可用坐标；5XZC
只覆盖目标的一部分，实际具有坐标的目标残基为 232/393。这说明“序列相同”和“结构可以直接
使用”不是同一件事。

**可能遇到的问题**

可能把关键区域缺失的结构继续用于后续分析，造成结果不可靠；也可能错误放弃原本足够使用的实验
结构，增加不必要的预测成本。即使两个结构的总体覆盖率相同，如果缺失位置不同，它们的实际用途
也可能完全不同。

**希望得到的解决方案**

希望算法负责人给出一套结构可用性标准，明确最低坐标覆盖率、允许缺失多少残基、哪些关键区域
不能缺失，以及实验方法和分辨率等质量要求。结构不满足要求时，还要明确是完全放弃、有限使用，
还是重新预测，并提供几组刚好通过和刚好不通过的边界案例。

---

### D13：同一结构记录中多个结构对象的选择

**目前情况**

一个 PDB 结构记录中可能同时存在多条蛋白链、多个结构模型、不同的生物学组装方式，以及同一原子
的多个可选位置。我们已经确认这些信息都必须保留，但还没有决定最终使用哪一个结构对象。

**可能遇到的问题**

同一个 PDB 编号在不同运行中可能选到不同蛋白链或不同组装体，导致坐标、蛋白界面和表面暴露度
等后续结果不一致。这样即使输入完全相同，也可能因为选择对象不同而得到不同分析结论。

**希望得到的解决方案**

希望算法负责人明确：优先使用原始结构单元还是具有生物学意义的组装体；多条相同蛋白链、多个
结构模型和多个原子位置怎样选择；几个候选条件相同时按什么顺序处理。最终规则应保证同一输入在
相同数据版本下总能选到同一个结构对象，并用多链、多模型和多组装体样本进行验证。

---

### D14：RCSB、AlphaFold DB 与 BLAST 的查询策略

**目前情况**

当前可使用的三类信息来源分别是：RCSB 实验结构库、AlphaFold DB 公共预测结构库，以及 BLAST
相似性检索。它们是结构获取过程中的不同信息来源，并不代表每次都必须全部查询。实测中，O15116
在 RCSB 没有查到目标结构，但在 AlphaFold DB 中存在与目标序列完全一致的预测模型。

**可能遇到的问题**

同一条序列可能因为查询顺序不同或某个外部服务临时故障而得到不同结论，也无法可靠判断什么时候
可以宣布“没有合格的已有结构”。如果每次都查询全部来源，又可能增加不必要的时间和外部服务
压力；如果过早停止，则可能漏掉更合适的结构。

**希望得到的解决方案**

希望算法负责人明确三类来源的先后顺序、哪些必须查询、哪些可以按情况使用，以及什么时候可以
提前停止。还需要说明某个来源失败时能否依据其他来源继续，以及公共预测结构是否可以作为“已有
结构”使用。最终形成一套固定的查询和异常处理规则。

---

### D15：从输入序列找到正确的 AlphaFold DB 记录

**目前情况**

项目的权威输入是蛋白序列，UniProt 编号只是可选的查询提示；但 AlphaFold DB 通常需要它所支持的
蛋白编号。实测中，O15116 可以正常取得模型，而 RefSeq 编号 `WP_505187596.1` 不能直接用于查询。
因此，只有序列时并不一定能直接找到正确的 AlphaFold DB 记录。

**可能遇到的问题**

可能漏掉正确的预测模型，也可能因为物种或编号歧义而查询到错误蛋白；还可能让外部编号错误覆盖
用户提交的目标序列。一条序列如果同时对应多个蛋白编号，而系统没有物种等辅助信息，也无法可靠
判断应该选择哪一个。

**希望得到的解决方案**

希望产品和算法负责人共同确定一个权威的序列到 UniProt 编号识别方案，并明确是否必须结合物种
信息。对于找不到编号、找到多个编号，或者编号对应序列与输入不一致的情况，需要分别说明是跳过
AlphaFold DB、提示错误，还是采用其他方式继续；无论哪种情况，都不能改变用户提交的目标序列。

---

### D16：BLAST 的用途、数据库和阈值

**目前情况**

RCSB 自带的序列相似性检索与独立运行的 BLAST 不是同一种方法，两者的评分也不能直接比较。前期
实测已经成功运行 BLAST，但其中一个无明确目标结构的样本仍得到 42 个较弱命中，最佳命中的
显著性也不足以让开发团队判断它是不是可用模板。

**可能遇到的问题**

无法判断 BLAST 是否必须执行，也无法说明它的结果会不会改变候选集合；开发阶段使用的宽松参数
还可能被误当成正式科学标准。门槛过宽会产生大量没有实际价值的弱命中，门槛过严又可能漏掉真正
有用的同源模板。

**希望得到的解决方案**

希望算法负责人说明 BLAST 到底用于补充检索、发现同源模板还是交叉验证，并确定使用的数据库和
版本、什么情况下运行、什么情况下跳过，以及序列一致程度、覆盖范围和显著性门槛。BLAST 与 RCSB
发现同一结构时，也需要规定怎样合并和排序，并用明确的有效、无效和边界样本验证。

---

### D17：输入序列字符与长度边界

**目前情况**

公开蛋白序列中可能出现 B、O、U、X、Z 等特殊字符，不同检索工具对特殊残基、未知残基、终止符、
空白和超长序列的接受范围并不一致。如果每个工具自行处理，同一份输入可能被转换成不同的序列。

**可能遇到的问题**

可能出现入口检查通过但后续工具失败的情况，也可能导致不同来源实际查询的不是同一条序列，破坏
结果的一致性和可复现性。更严重的是，如果某个工具静默删除或替换特殊字符，查询对象可能已经不再
是用户原来提交的蛋白。

**希望得到的解决方案**

希望算法负责人明确哪些字符可以保留、替换或拒绝，以及空白、大小写、序列标题和终止符怎样统一
处理；同时给出允许的最小和最大长度。开发团队再据此建立一套统一检查规则，确保所有查询来源看到
的是同一条序列，并对空序列、格式错误、特殊残基和超长序列分别测试。

---

向上确认不能只得到“原则上同意”这样的口头结论。每项反馈都应记录负责人、确认日期、规则版本、
具体判断标准、边界样例和适用范围；收到这些内容后，开发团队才能把规则落实到工具和测试中。
