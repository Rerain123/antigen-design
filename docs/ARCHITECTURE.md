# 架构

## 职责与调用关系

客户端通过 REST / MCP 提交、查询、控制任务并获取附件。`service_api/` 提供传输层、认证、任务接口和面向工作流的封装；`runtime.py` 及相关模块负责持久化状态、幂等、产物注册与恢复。Worker 从运行目录领取工作，将工具输出转换为可校验结果。

`resident_process.py` 与 `resident_result.py` 管理子进程和结果收据。`unified_gpu_worker.py` 提供 GPU 工作的排队与独占执行机制。Linux 入口和 Windows 入口分别适配进程与文件系统差异；工具运行环境由外部配置决定。

`development/` 包含结构、同源性、表位、序列设计、可开发性等离线工具适配，以及工作流控制逻辑。`t01_structure_mapping` 处理结构编号、残基对应与结构消费前检查。工具依赖独立环境，不能假定控制服务的 Python 环境已安装所有科学软件。

## 数据契约与可追溯性

工程 JSON Schema 位于 `工作流设计/02-数据契约/`。运行时按契约校验请求、控制动作和任务状态。产物通过路径、注册身份与 SHA-256 联系到对应运行，执行配置还会绑定实现及必要外部资料的版本指纹。

保留目录名称是为了兼容代码中的契约定位。公开导出保留源码字节；个别测试中记录的设备标识已替换为虚构标识，详情见 [源码清单](SOURCE_MANIFEST.json)。

## 科学边界

LLM 与 Dify 不代替科学计算或门控。后端固定执行规则与校验，缺失输入或未满足条件时保留失败、未评估或阻塞事实。工程源代码中的规则实现不能替代专家原件，也不代表专家验收。

工作流保留业务节点与设计确认、WT、重算及条件分支的边界；N08 和 N18 / Agent C 存在延期范围。此仓库不声明所有节点已具备完整科研消费资格。原件、数据包和运行证据未公开，相关具体结论应由项目负责团队依据其持有资料核对。
